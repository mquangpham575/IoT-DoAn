# Integration Guide for Members 1, 2, 3 and 5

## 1. Purpose

This guide explains how other team members should integrate their parts with the Backend & Edge Logic module.

The backend supports both:

```text
POST /data
POST /api/v1/sensor/readings
```

This means the current firmware can continue using the old `/data` endpoint, while future versions can use the standardized `/api/v1/sensor/readings` endpoint.

## 2. Shared System Flow

```text
Sensors / ESP32
      |
      v
Backend API
      |
      v
Backend Edge Logic
      |
      v
SQLite Database
      |
      v
Dashboard / Android App / Discord Alert
```

## 3. Shared Payload Contract

Recommended payload:

```json
{
  "device_id": "esp32_01",
  "temperature": 30.5,
  "humidity": 72.0,
  "gas": 1250,
  "light": 650,
  "noise": 320
}
```

Minimum payload accepted by legacy firmware flow:

```json
{
  "temperature": 30.5,
  "humidity": 72.0,
  "gas": 1250,
  "light": 650,
  "noise": 320
}
```

## 4. Guide for Member 1 - Hardware

### 4.1. Responsibility

Member 1 is responsible for physical hardware setup, wiring, and checking sensor stability.

Current expected components:

```text
ESP32 DevKit
DHT22
MQ135
BH1750
MAX4466
Buzzer
LED
```

### 4.2. Expected Pin Mapping

```text
DHT22       -> GPIO 4
MQ135       -> GPIO 34
MAX4466     -> GPIO 35
BH1750 SDA  -> GPIO 21
BH1750 SCL  -> GPIO 22
Buzzer      -> GPIO 18
LED         -> GPIO 19
```

### 4.3. What Member 1 Should Provide

Member 1 should provide:

- Photo of wiring.
- Confirmation that all sensors power on.
- Confirmation that ESP32 Serial Monitor prints sensor values.
- Any known hardware instability, for example noisy MQ135 or unstable microphone values.
- Short video showing ESP32 running with sensors.

### 4.4. Hardware Test Checklist

- [ ] ESP32 powers on.
- [ ] DHT22 returns temperature and humidity.
- [ ] MQ135 returns analog value.
- [ ] BH1750 returns lux value.
- [ ] MAX4466 returns sound/noise analog value.
- [ ] LED works.
- [ ] Buzzer works.
- [ ] All GND lines are connected.
- [ ] Sensor values are printed in Serial Monitor.

### 4.5. Important Note

The device is a fixed monitoring node. It should stay in one place during real testing.

Recommendations generated by backend are for people managing the environment, not for moving the device.

## 5. Guide for Member 2 - Firmware and ESP32 Edge Logic

### 5.1. Responsibility

Member 2 is responsible for ESP32 firmware, sensor reading, local LED/Buzzer alert, WiFi connection, and HTTP sending.

### 5.2. Current Backend Compatibility

Firmware can continue using:

```text
POST /data
```

No forced migration is required.

If firmware owner agrees, future firmware can use:

```text
POST /api/v1/sensor/readings
```

### 5.3. Required HTTP Headers

```text
Content-Type: application/json
X-API-KEY: IOT_SECRET_2026
```

### 5.4. Important Firmware Configuration

Do not use:

```cpp
const char* serverUrl = "http://localhost:8000/data";
```

Use PC/Laptop LAN IP:

```cpp
const char* serverUrl = "http://192.168.1.10:8000/data";
```

or:

```cpp
const char* serverUrl = "http://192.168.1.10:8000/api/v1/sensor/readings";
```

### 5.5. What Member 2 Should Provide

Member 2 should provide:

- Current firmware file.
- Serial Monitor logs.
- HTTP response code.
- JSON payload being sent.
- Confirmation whether firmware uses `/data` or `/api/v1/sensor/readings`.

### 5.6. Successful Firmware Integration

Integration is successful when Serial Monitor shows:

```text
WiFi connected
HTTP Response code: 200
```

and dashboard shows a new reading.

### 5.7. Local Edge Logic Boundary

ESP32 local edge logic should stay simple:

- Turn LED on when threshold is exceeded.
- Trigger buzzer for warning.
- Print local warning to Serial Monitor.

Complex logic should stay in backend:

- Risk score.
- Multiple-condition assessment.
- Recommendation.
- Discord alert.

## 6. Guide for Member 3 - AI and Rule-Based Logic

### 6.1. Responsibility

Member 3 is responsible for AI/rule-based assessment logic.

Backend currently supports rule-based edge logic in:

```text
backend/app/services/edge_service.py
backend/app/services/comfort_service.py
backend/app/services/alert_service.py
```

### 6.2. Current Backend Output

The backend generates:

```text
comfort_level
status_label
risk_score
reasons
recommendation
```

Example:

```json
{
  "comfort_level": 1,
  "status_label": "WARNING",
  "risk_score": 45,
  "reasons": [
    "High temperature",
    "Poor air quality / high gas concentration"
  ],
  "recommendation": "Không khí có dấu hiệu kém an toàn. Nên tăng thông gió..."
}
```

### 6.3. Where to Improve Logic

If Member 3 wants to adjust thresholds:

```text
backend/app/services/edge_service.py
```

If Member 3 wants to adjust recommendation text:

```text
backend/app/services/alert_service.py
```

If Member 3 wants to add an AI model later:

```text
backend/app/services/comfort_service.py
backend/ml/
```

### 6.4. Important Design Rule

Recommendations must be human-centered.

Good:

```text
Nên tăng thông gió, mở cửa hoặc kiểm tra xem trong phòng có khói, mùi lạ hay nguồn khí bất thường không.
```

Avoid:

```text
Di chuyển thiết bị ra khu vực yên tĩnh hơn.
```

Reason:

- ESP32 is a fixed monitoring node.
- Recommendation should guide people to improve the monitored environment.
- Recommendation should not suggest moving the monitoring device.

### 6.5. What Member 3 Should Provide

Member 3 should provide:

- Threshold rationale.
- Explanation of NORMAL / WARNING / CRITICAL.
- Any AI model if used.
- Model input/output description.
- Justification for risk score rules.

## 7. Guide for Member 5 - Android / Mobile App

### 7.1. Responsibility

Member 5 is responsible for mobile app display and user interaction.

The mobile app should read from backend API. It should not duplicate backend edge logic.

### 7.2. Recommended APIs

Latest reading:

```text
GET /api/v1/sensor/latest
```

History:

```text
GET /api/v1/sensor/history?limit=20
```

Health check:

```text
GET /api/v1/system/health
```

Legacy history still exists:

```text
GET /history?limit=20
```

but new mobile app should prefer the standard `/api/v1` APIs.

### 7.3. Expected Mobile Display

Mobile should display:

- Connection status.
- Latest temperature.
- Latest humidity.
- Latest gas.
- Latest light.
- Latest noise.
- Status label.
- Risk score.
- Recommendation.
- Recent trend chart if possible.

### 7.4. Backend URL Rule

On Android, do not call:

```text
http://localhost:8000
```

unless the backend is inside the Android device itself.

Use PC/Laptop LAN IP:

```text
http://192.168.1.10:8000
```

The app can allow user to input backend URL manually.

### 7.5. What Member 5 Should Provide

Member 5 should provide:

- App screenshot showing backend connection.
- App screenshot showing latest sensor data.
- App screenshot showing WARNING or CRITICAL state.
- Error message if app cannot connect to backend.
- Confirmation which API endpoint the app is calling.
